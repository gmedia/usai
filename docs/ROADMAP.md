# Roadmap to production-ready

> The phase decides what work is allowed. From here on the work is
> **qualification, not capability**: every phase removes reasons a developer
> or an operator still has to distrust Usai. Features are added only when a
> phase proves a real application cannot be built without them.

Current phase: see `STATUS.md`. Versions stay `0.0.x` until RC; breaking
changes are allowed and preferred over carrying a wrong abstraction.

| Phase | Focus | Exit criteria |
|---|---|---|
| **P3** | Dogfood fixes | The fresh-eyes report's contract/correctness items closed; a fresh scaffold installs, typechecks, tests and runs without friction. **Done in 0.0.2**; `fetch`/`crypto` as host capabilities was decided by ADR-0017 and shipped (`httpClient`, the crypto subset). |
| **P3.5** (done 2026-09-18: v0.0.4) | Distribution & container UX | Native binary, npm packages and Docker images (`sakaladev/usai:<v>` runtime, `<v>-dev` builder) from **one tag**; linux/amd64 + linux/arm64; `docker compose up` path in the scaffold; runtime image non-root, no toolchain, read-only artifact, graceful SIGTERM; artifact↔runtime compatibility refused deterministically before serving; container smoke test in CI. Docker is a zero-install path, never the only path. |
| **P4** (done 2026-09-18: `examples/invoicing`, ADR-0017) | Real application | One realistic application — auth, tenants, CRUD with transactions and pagination, validation, errors, background task, cron, queue, outbound HTTP, migrations, seeders — built and used as a user, not as the author, without touching runtime internals. If a fundamental primitive is missing, that is the finding (outbound HTTP becomes an ownership-aware host operation here, not a polyfill). Boring is the goal. |
| **P5** (done 2026-09-18: runbooks, campaign) | Operational qualification | Deployed for real (reverse proxy → Usai → PostgreSQL) for days; deliberately broken: runtime restart, PostgreSQL kill/restart, network interruption, bad deployment, rollback, rapid revision replacement, traffic spike, memory pressure, near-full disk, SIGTERM, forced kill, invalid config. A runbook per incident: which metric moves, which log line appears, what workloads do, when recovery happens — without reading Rust. |
| **P6** (campaigns done 2026-09-18; WebSocket/stream campaign 2026-09-19; **24 h and 72 h soaks passed**, the 72 h run appended 2026-09-23) | Reliability qualification | 24 h and 72 h realistic soaks with a memory plateau and zero ownership/state leak; revision churn (deploy A, B, rollback A, C, broken D refused, E …) thousands of times under traffic; DB flap, idle→burst, overload, shutdown/restart loops, queue retry/dead-letter, WebSocket/stream churn, artifact upgrade/rollback. Repeated, not passed once. |
| **P7** (kit: `docs/P7-EXTERNAL-VALIDATION.md`, report template `.github/ISSUE_TEMPLATE/p7-report.yml`) | External validation | 3–10 developers with no context build and deploy a small API from the public docs alone. Measured: time to hello world, time to PostgreSQL, what was misunderstood, which API needed the source, which errors did not help, whether the lifecycle model felt natural. Five people making the same mistake means the API is wrong. |
| **P8** (opened 2026-09-19; c=1 phase done the same day, `docs/measurements/2026-09-19-p8-parity.md`; **the concurrency sweep is in, 2026-09-23: `docs/measurements/2026-09-23-sweep.md`** — one Usai process is ahead of one Node process from c=8 up on every class and 2× behind an eight-worker cluster on the database classes; the runtime tax is 6–14× Node's CPU on a trivial route and disappears where PostgreSQL does the work) | Production hot-path parity | The per-request **invoice** (`USAI_PROFILE=1 … profile_matrix http_invoice`: host phases, runtime/driver/engine phases, the guest's own ledger) for three workload classes — hello, contract-heavy, PostgreSQL CRUD — shows where the implementation pays what the semantics never asked for; those costs are removed without weakening any contract (the direct-call guest ABI instead of `eval`, ADR-0018; one validation when the schema is proven structural; the bookkeeping audit against the research checklist), measured before/after on the same pinned core, both engines green. The research representation (R3: +51 µs p50 over Node/Fastify at c=1 on HTTP+PostgreSQL) is the oracle, not a target. Comes before RC because the guest ABI is part of what RC freezes. |
| **P8E** (2026-09-19/20; **floors re-measured 2026-09-23** — `docs/measurements/2026-09-23-floor-accounting.md`: the boxed cells were not charged for the binary they measured, so the two numbers below are superseded — supported floor **192 MiB** stands, technical floor is **64 MiB, not 48**; density is unaffected) | Efficiency envelope | The other axis of parity, measured before RC: the **technical floor** (one hello-only application in a cgroup box: ~~48 MiB / 0.25 vCPU~~ — re-measured as **64 MiB**; 32 MiB is OOM-killed), the **supported floor** (the production shape with PostgreSQL, task, cron, status + metrics, 48 worlds: 192 MiB / 1 vCPU with ≥ 25 % headroom, written into `SUPPORTED.md`), and **density** (N = 1…50 mostly-idle applications on one host against Node + Fastify: ≈30 MiB PSS and 0.00 % CPU per idle Usai application vs ≈36 MiB / 0.12 %; cold first response 11–16 ms vs 45–62; ≈1.7× more CPU per request under burst). Only measured idle costs were fixed (the watchdog and epoch tickers park while no world is live: 300 wakeups/s → 0). Found against the model's prediction: memory does not return after a burst — the pool keeps ≈4 MiB RSS per touched slot (`USAI_WASM_KEEP_RESIDENT`, measured both ways in the report). The multi-application runtime process is recorded as Q17, not attempted. P9 (hot path) is decided from this, the P8 invoice and the concurrency sweep. |
| **RC / Beta** | Freeze-ish contracts | `http.*`, `task`/`cron`/`command`/`service`/`queue`, resources, env, config, artifact format, CLI stable; upgrade/downgrade matrix (runtime × artifact × SDK) regression-tested; `SUPPORTED.md` written. The inventory this needs is `docs/CONTRACT-FREEZE.md` (2026-09-23): every surface, what freezing it commits us to, the five things still moving, and the three ways to take the decision — including staying `0.x` and saying so louder. |
| **Production Ready** | Every gate green | Automated evidence **and** real operational evidence **and** external developer evidence. Also: artifact signing/attestation verified before activation (`cache/image.cwasm` is native code); observability round two (latency histogram, error rate, admission rejections, live worlds, task/queue state, pool/quarantine, revision state, CPU/memory pressure); the vendored Wasmtime patch upstreamed or with documented provenance and a rebase test; security qualification inside the supported envelope (fuzzing of contracts, artifacts and the control API; dependency scanning; secret-leak checks; body/timeout/memory limits). Comparative benchmarks follow the suite in `docs/measurements/BENCHMARKS.md` — several workload classes, four scoreboards, comparators doing the same work (Node/Fastify, Bun/Hono, Deno/Hono, PHP-FPM, a Rust-native control) — reported as they come out; no single benchmark is the benchmark. **Where each stands, 2026-09-23:** artifact signing/attestation — done and decided (ADR-0020), verified from outside by `scripts/qualification/threat/run.sh`; observability round two — done (latency histogram, rejections by reason, per-workload classes and CPU, live worlds, task/queue state, pool/quarantine, revision state, process memory); the vendored Wasmtime patch — **merged upstream** and waiting only for a release to vendor from; security qualification — fuzzing now covers the guest bridge and the SQL parameter conversion, dependency scanning and **secret scanning** are in CI, and the body/timeout/memory limits are probed by the threat campaign; comparative benchmarks — the sweep plus saturation to c=512. **What is left is not automated evidence:** P7 (people), the three-replica and multi-day campaigns (running), and the contract freeze (`docs/CONTRACT-FREEZE.md`, a maintainer's decision). |

## Not blockers for the first production-ready

HTTP/2, built-in HTTP TLS, Redis, Kafka, Node compatibility, a hostile
multi-tenant sandbox, an ORM, multi-region, every Web API. Production-ready
means: *within the environment we declare supported, Usai can be run,
upgraded, loaded, failed, recovered and observed with proven behaviour* — not
feature parity with anything.

## Distribution paths (P3.5 onward)

```text
1. native binary        usai dev               (first-class; releases page)
2. Docker               docker compose up      (zero-install, not zero-cost: bind mounts on macOS/Windows)
3. npm-assisted binary  pnpm usai dev          (the SDK's `usai` bin fetches the release binary at its version, once)
```

Three artefacts from one tag `vX.Y.Z`: GitHub release binaries, npm
`@sakaladev/usai` + `@sakaladev/create-usai`, Docker `sakaladev/usai:X.Y.Z`
(+ `X.Y`, `X`, `latest`) and `X.Y.Z-dev`. No version skew between them.
