# Fuzzing (2026-09-20, local, 20 minutes per target)

The three libFuzzer targets of `fuzz/` (`fuzz/README.md`) run for 20 minutes
each on the development machine (WSL2, one core per target, `cargo +nightly
fuzz run <target> -- -max_total_time=1200 -timeout=20 -rss_limit_mb=4096`),
at commit `e408072`. The seeds tracked in `fuzz/corpus/<target>` were the
starting corpus; the units a run adds are ignored by git. CI runs the same
targets for two minutes per push that touches `crates/` or `fuzz/` and ten
minutes nightly, uploading a reproducer on a crash.

| Target | What it exercises | Executions | exec/s | Edge coverage (`cov`) | Features (`ft`) | Corpus after | Peak RSS | Crashes / timeouts / OOM |
|---|---|---|---|---|---|---|---|---|
| `manifest` | `manifest.json` bytes → `Manifest` deserialization → `ApplicationDefinition::new` → OpenAPI (both profiles) → graph → router path conversion → cron schedule parsing → env validation | 22 251 064 | 18 527 | 5 409 | 18 109 | 4 922 units, 6.4 MB | 620 MB | **0 / 0 / 0** |
| `http_boundary` | query string → JSON, scalar coercion against a schema, the guest's HTTP output rendered as a response (headers, repeated headers, body encodings) | 27 031 645 | 22 507 | 3 725 | 16 576 | 4 134 units, 1.2 MB | 681 MB | **0 / 0 / 0** |
| `sourcemap` | source map parsing (VLQ), position lookup, stack mapping | 28 774 044 | 23 958 | 2 581 | 10 290 | 4 053 units, 1.5 MB | 559 MB | **0 / 0 / 0** |

78 million executions, no crash, no hang past the 20 s timeout, no
allocation past 4 GB. Coverage kept growing slowly through the twenty
minutes (`NEW_FUNC` lines late in every log), so the corpus is not saturated
— the nightly CI run keeps extending it.

What this does and does not say: the parsers where trust changes hands
(an artifact from disk, a request from the network, a source map from the
build) do not panic or hang on 78 million mutated inputs. It said nothing
about the guest or about the PostgreSQL path, which were the two blind spots
this report named; **both are targets since 2026-09-23**:

- `guest_bridge` — the host's side of the bridge protocol: the
  `kind\0payload` framing every world call arrives in, a log line's
  `message\0{fields}` framing, the shapes each builtin kind decodes out of a
  payload, and the completion identifiers the guest hands back. A bug in the
  guest, or in a core built from sources we did not write, must not be able
  to panic the host. 3.8 M executions on the first run, 0 crashes.
- `postgres_params` — the conversion every application parameter goes
  through: arbitrary JSON against the twenty-two wire types an application
  binds in practice (including the ones whose text form the runtime parses
  itself: interval, inet, arrays, numeric). The values are the application's,
  the types are the server's, and everything between them is ours. 2.8 M
  executions on the first run, 0 crashes.

Longer sessions the same day, after the first runs: `guest_bridge` 1.5 M more
executions (corpus 1 537 units, coverage 1 514 edges) and `postgres_params`
4.0 M (corpus 2 735 units, 3 891 edges), both with 0 crashes and 0 artifacts.
The corpora are the seeds plus what those runs found; the nightly CI keeps
extending them.

Still outside: the **QuickJS core itself** (a third-party C codebase; its own
project fuzzes it) and the **PostgreSQL wire protocol** as decoded by
`tokio-postgres` — a real server is the oracle for that one
(`tests/postgres.rs`). The control API and artifact
loading are covered by the mutation suite in `tests/robustness.rs` (600
malformed artifacts, 600 malformed requests), which the nightly CI runs too.

Raw logs: the session's scratch directory (`fuzz-out/<target>.log`); the
numbers above are libFuzzer's own `-print_final_stats=1` output.
